# Testing plan: one per-user store, and tags on a session

Obligations for `plans/global-store/design.md`, one leaf per behavior, grouped by the level each runs at. Nothing here is test code; the implementer discharges each leaf and the auditor traces it to the evidence the leaf names.

The corpus everywhere below is the recorded fixtures `tests/conftest.py:fixture_trace` builds (`SPINE`, `FORK_ORIGIN`), which are redacted real sessions. Tag pairs are the one invented input in this change and honestly so: no transcript carries a tag, because a tag is the caller's word (design, "Key contracts"). Every leaf whose data is invented says so.

## Slice 1 — the store path

- **unit (`tests/test_store_path.py`)** — no store, no disk: `default_store()` under a monkeypatched environment and a monkeypatched `platformdirs.user_data_path`
  - `HP_DB` set names the store exactly, with no directory joined onto it. *Evidence:* `monkeypatch.setenv("HP_DB", tmp_path / "elsewhere.duckdb")`; assertion compares the whole `Path`, and `platformdirs.user_data_path` is monkeypatched to raise so a leaf that consults it fails loudly
  - `HP_DB` unset falls to `user_data_path("hyphae") / "traces.duckdb"`. *Evidence:* `monkeypatch.delenv("HP_DB", raising=False)` plus a `user_data_path` stub returning `tmp_path`; assertion on the joined path, and on the single call's argument (`"hyphae"`), so the app name cannot drift
  - **`HP_DB` set but empty refuses rather than falling back.** *Evidence:* `monkeypatch.setenv("HP_DB", "")`; the raised error names `HP_DB`. The design does not say what an empty value means — see *Design findings*
  - `default_store()` touches no disk: it neither creates the directory nor the file. *Evidence:* the stubbed `user_data_path` returns a path under `tmp_path` that does not exist; assertion that it still does not exist after the call
  - A first write under a store path whose parent does not exist creates it. *Evidence:* `DuckDbExporter(tmp_path / "nested" / "deep" / "traces.duckdb", wait=NO_WAIT)` then `stored_rows`; today's `mkdir(parents=True)` in `DuckDbExporter.__init__` has no leaf naming it, and the per-user default is what makes it load-bearing
- **unit (`tests/test_cli.py`)** — the parser only, built and asked to parse; no store is opened
  - Every store-taking subcommand still defaults `--db` to one resolved path, and the pinned argument table reads it from a monkeypatched `HP_DB` rather than the developer's ambient one. *Evidence:* the table at `tests/test_cli.py:72-111` swaps `DEFAULT_DB` for the monkeypatched value; `test_a_subcommand_parses_to_the_arguments_it_documents` and `test_the_store_flag_is_one_flag_wherever_it_appears` both stay green. A suite that reads the real `HP_DB` passes or fails with the machine, which is the trap here
  - **`--db`'s help line prints the resolved path.** *Evidence:* `cli.build_parser()` under a monkeypatched `HP_DB`, then the extract subparser's `format_help()` contains `str(default_store())`. This is what makes the parser resolve at build time rather than at import, which is also what lets the leaf above monkeypatch it
  - `hp query --list` works from a directory with no `data/`. *Evidence:* the design names it as a hand check; as a leaf it is `cli.main("query", "--list")` with `HP_DB` pointed at a `tmp_path` store and `monkeypatch.chdir(tmp_path)`, asserting the listing prints and no `data/` appears under the cwd

## Slice 2 — tags

- **integration (`tests/export/test_duckdb.py`)** — a real DuckDB file in `tmp_path`, written by `DuckDbExporter` and read back with a bare connection through `tests/conftest.py:stored_rows`
  - A trace exported with tags reads back as one row per pair. *Evidence:* a recorded fixture trace plus invented pairs `{"batch_id": "b1", "task": "t1"}` (invented: the caller supplies them); `SELECT key, value FROM session_tags WHERE session_id = ?` compared as a whole sorted list
  - **A re-extract with different tags replaces the set — no pair from the first write survives.** *Evidence:* export with `{"batch_id": "b1", "set": "s1"}`, re-export the same session with `{"batch_id": "b2"}`; the read-back equals `[("batch_id", "b2")]` exactly. This is the delete-then-insert rule reaching the new table
  - **A re-extract with no tags clears them.** *Evidence:* the same session re-exported with `tags={}`; `SELECT count(*) FROM session_tags WHERE session_id = ?` is `(0,)`. The design's stated semantics — "a tag is a property of the extraction" — stand or fall here
  - One session's re-export leaves another session's tags alone. *Evidence:* extend `test_a_replace_leaves_other_sessions_alone` to two tagged sessions; the untouched session's pairs compare equal before and after
  - `session_tags` is a member of `TABLES`, so the census a round-trip takes counts it. *Evidence:* `test_a_trace_round_trips`'s `counts()` map gains the table; a `TableSpec` added to `_SCHEMA` but not to `TABLES` shows up as a missing key
  - Two pairs with the same key in one export violate the primary key and roll the whole export back. *Evidence:* the `test_a_failed_export_changes_nothing` pattern — a `Mapping` cannot carry a duplicate key, so this leaf plants the duplicate on `SessionTrace.session_tags` directly (invented, and the shape is the point); the store's row counts compare equal before and after
  - `tags` reaches the exporter from the CLI through the pipeline seam, not around it. *Evidence:* `src/hyphae/pipeline.py:47` `Exporter` Protocol and `refresh()` at line 91 take `(trace, fingerprint)` and nothing else today, so one of them has to carry the pairs; a fake exporter in the pipeline tests records what `refresh` handed it, asserting the pairs arrive per session. **Reachable once slice 2 picks the seam** — the design leaves it open (`export`'s signature versus a `SessionTrace` field the CLI fills). Either answer discharges the leaf; write the assertion against whichever the slice picks, and against the exporter's per-session write in the meantime
  - Parsed `--tag` pairs travel from `argparse` into the exporter call. *Evidence:* `cli.main("extract", …, "--tag", "batch_id=b1")` against a `tmp_path` store, then `stored_rows` on `session_tags` — the end-to-end leaf that no unit-level parse assertion covers
- **unit (`tests/test_cli.py`)** — the parser and `_extract`'s argument handling
  - `--tag` repeats and parses into a mapping in argument order. *Evidence:* `parse_args(["extract", …, "--tag", "a=1", "--tag", "b=2"])`; `args.tag == ["a=1", "b=2"]` and the parsed mapping compares whole
  - A value containing `=` splits once, keeping the rest of the value intact. *Evidence:* `--tag note=a=b` yields `{"note": "a=b"}` — the `split("=", 1)` contract `--param` already has
  - A `--tag` with no `=` is a parse error whose message names the flag. *Evidence:* `pytest.raises(SystemExit)`; the message is `--tag takes KEY=VALUE`
  - **An empty key is a parse error.** *Evidence:* `--tag =v` raises `SystemExit`. `--param` does *not* reject this today — see *Design findings*
  - `hp extract` with no `--tag` parses to an empty mapping, not `None`. *Evidence:* the pinned argument table in `test_cli.py` gains `"tag": []`; `test_every_subcommand_the_parser_exposes_is_pinned_above` holds the table to the parser
- **integration (`tests/export/test_duckdb__migrations.py`)** — a real store aged in place by inverting the newer steps, then opened by this build
  - **A version-7 store crosses the new step and comes out holding `session_tags`, empty, with every existing row still readable.** *Evidence:* `old_store()` gains the inverse of the new step (`DROP TABLE session_tags`) and `OLDEST_MIGRATABLE` still derives from `min(MIGRATIONS)`; `test_an_older_store_is_migrated_and_keeps_its_rows` asserts the briefs, the replayed-compaction sets, `stamped_version(db) == SCHEMA_VERSION`, and `SELECT count(*) FROM session_tags` is `(0,)`
  - **The migrated store passes `check_shape`.** *Evidence:* the migration's `CREATE TABLE` and `_SCHEMA`'s must agree column for column; the migration test's `shape(path)` for `session_tags` equals the shape a fresh store gets from `_SCHEMA` alone. `DuckDbExporter.__init__` runs `migrate` then `check_shape`, so a migration that spells a column differently opens fine and dies at the first insert
  - No version between the oldest migratable store and this build lacks a step. *Evidence:* `missing_steps(OLDEST_MIGRATABLE) == []`, asserted where `SCHEMA_VERSION` bumps; the existing `test_a_schema_version_no_migration_reaches_refuses_to_open` covers the refusal, not the gap
  - A store already at the new version is migrated by no step. *Evidence:* `test_a_current_store_is_migrated_by_no_step_at_all` unchanged and green
- **integration (`tests/analyze/test_macros.py`)** — the macros installed on a real DuckDB connection, run as SQL
  - `tagged(k, v)` answers the session ids carrying that exact pair and nothing else. *Evidence:* a store with two tagged sessions (invented pairs) and one untagged; `SELECT * FROM tagged('batch_id', 'b1')` compares to the one expected id. The macro reads a stored table, so this leaf needs a store, not the in-memory connection the other macro leaves share
  - An unknown pair answers zero rows rather than raising. *Evidence:* `tagged('nope', 'nope')` returns `[]` — an absence a query can join on
  - `needed_by()` includes the macro set for a statement that calls `tagged`. *Evidence:* `needed_by("SELECT * FROM tagged($key, $value)")` is `SETUP`, which is what makes the viewer's query page print the definitions
- **integration (`tests/analyze/test_queries.py`)** — every shipped `.sql` run against a real store, plus the library's static rules
  - The example tag query runs with `key` and `value` bound. *Evidence:* `test_every_query_runs` picks it up by parametrization once the tier's binding table (`tests/analyze/test_queries.py:303`) and `PARAM_TYPES` carry the two parameters
  - The two new parameters are declared and bound by a shipped statement. *Evidence:* `test_every_default_and_param_type_is_bound_by_a_shipped_query` stays green — a `PARAM_TYPES` entry no query binds fails it
  - **The example query counts through the corpus views.** *Evidence:* `test_a_cross_session_query_counts_through_the_corpus_views` reads the bare identifiers of the file, and `tagged(...)` hides `session_tags` from that scan — so this leaf must additionally assert the query joins `tagged` against `corpus_*` and not the raw tables. See *Design findings*

## Slice 3 — extract under an open viewer connection

- **process (`tests/export/test_duckdb__locking.py`)** — real DuckDB file locks across processes; the holder is always a subprocess, because this process's own second open answers differently (`tests/conftest.py:locked`)
  - **An extract lands once a reader that opened the store the way a viewer page does lets go, inside `CLI_WAIT`.** *Evidence:* a read-only holder **in a subprocess** — `read_only=True`, `wait=PAGE_WAIT`, the arguments `view/store.py:open_store` passes — with `hold=BRIEF_HOLD`; `DuckDbExporter(db, wait=CLI_WAIT).export(...)` inside the block, then `stored_rows` shows the session. Cross-process is not a detail: this process's own second open succeeds whatever the file lock says, so an in-process reader tests the wrong failure (`tests/conftest.py:locked`). The realistic collision is one request long, because `open_store` opens read-only per request and closes
  - An extract against a reader that never lets go raises `StoreLocked` naming the holder, rather than hanging or corrupting. *Evidence:* the `locked(db)` default hold with `wait=IMPATIENT`; `pytest.raises(StoreLocked)` and the message carries the holder's pid, matching `test_a_writer_gives_up_with_a_clear_message`
  - After that refusal the store is still openable for write by anyone else. *Evidence:* `opens_elsewhere(db, read_only=False)` is true once the holder exits — the `test_a_refused_store_keeps_none_of_its_lock` pattern, so a refused extract leaks no lock of its own
  - A read-only holder exists to hold with. *Evidence:* `tests/conftest.py:_HOLDER` today calls `duckdb.connect(argv[1])`, which is read-write; the leaves above need a `read_only=True` variant, parameterized the way `_TAKER` already is. Not an obligation on its own — a seam the implementer builds first

## The docs the change touches

- **repo gate (`mise run check`)** — the doc tier: link and prose rules, plus the cog freshness check `cogs-check` runs over every generated block
  - **The docs slice 2 edits leave every cog block fresh.** *Evidence:* `mise run check` green, `cogs-check` included. `docs/schema.md`'s four field tables are generated by `tools/gen_schema.py` from the transcript record models in `src/hyphae/extract/records/`, and `session_tags` is a store table the caller fills, not a transcript field — so a hand-written row inside a generated block is erased by the next `mise run cogs` and reported by `cogs-check` before that. The design's file-tree diff puts `session_tags` in `docs/schema.md`; see *Design findings*

## Design findings

Four obligations the design's seam does not reach as written. None is dropped; each is stated at the level that proves the most.

- **"An empty KEY is a parse error, like `--param`'s" is false of `--param` today.** `dict(pair.split("=", 1) for pair in ["=v"])` is `{"": "v"}` — no `ValueError`, no `SystemExit` (`src/hyphae/cli.py:161`). Parity is reachable only by adding the empty-key check to both, through one shared helper. The `--tag` leaf above assumes that helper; if the change ships without it, the parity claim has to come out of the design
- **The corpus rule cannot see through the macro.** `test_a_cross_session_query_counts_through_the_corpus_views` scans bare identifiers in the query file, so a query calling `tagged(...)` satisfies it without reading a `corpus_*` view at all. The leaf above compensates with an explicit assertion, but the static rule has a hole any future macro widens
- **"The extract lands" under an open viewer connection is contradicted by evidence already in the repository.** `tests/conftest.py:locked`'s own docstring records it: "A read-only open takes a shared read lock, and DuckDB refuses a write open while one is held — so a wait that polled by opening could kill the very holder it waited for. It did, on CI run 31903080480." A viewer connection held for the length of an extract therefore blocks it. What saves the real case is that `view/store.py:open_store` holds the connection for one request only, which is why the first slice-3 leaf is written as *lands once the reader lets go*. If the design wants the stronger claim — an extract landing while a page is open — the fix is on hyphae's side, in how long a request holds the store, and no test can assert it into being
- **`session_tags` does not belong in `docs/schema.md`.** That document's tables are cog-generated from the transcript record models (`tools/gen_schema.py`, whose `SECTIONS` is closed on both sides), and its own lead says a field's meaning is declared on the model that carries it. A tag is written by the caller, not by Claude Code, so it has no record model and no citation. `docs/store.md` already owns the store's tables and the write rule; put it there and let the design's file-tree diff follow

## Not covered

- **`platformdirs`' own path convention per OS.** The unit leaves monkeypatch `user_data_path`, so they prove hyphae calls it with `"hyphae"` and joins `traces.duckdb`; what that resolves to on macOS versus Linux is the library's contract, tested by the library. The design's open question about `~/Library/Application Support/hyphae` is answered by running `hp query --list`, not by a leaf
- **The old `data/traces.duckdb`.** The design deliberately leaves it in place, so there is nothing to migrate and nothing to assert beyond `--db data/traces.duckdb` still opening it, which `test_the_store_flag_is_one_flag_wherever_it_appears` already covers
- **A tag filter in the viewer's session list.** Out of scope in the design; no page reads `session_tags` yet
- **The factory's side.** `plans/live-runs/design.md` lives in another repository and its keys (`run_id`, `batch_id`, `set`, `task`, `profile`) are the caller's words. Hyphae reserves none of them, so no leaf here names one as special
